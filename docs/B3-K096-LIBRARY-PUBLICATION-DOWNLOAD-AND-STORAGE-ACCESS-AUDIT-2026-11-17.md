## Executive summary

The repository contains two different public-library delivery paths. The standalone `library.html` page requests 60-second signed URLs, while the public homepage's embedded library constructs direct public URLs with `getPublicUrl()`. The admin page uploads, edits, publishes/unpublishes and deletes library records/files directly through the browser Supabase client.

The reviewed checked-in schema and migrations do not define `library_books`, the `avasin-library` bucket, or the associated table/storage policies. Consequently, the actual confidentiality boundary and the authorization of admin writes cannot be confirmed from this repository. The homepage's direct public URLs also mean the deployment is designed to work only if objects are publicly readable (or if the link is otherwise served by a public path); this is inconsistent with relying on short-lived signed URLs as the sole public-access mechanism.

## Confirmed implementation

1. `index.html` queries `library_books` for rows where `is_published = true`, then builds read and download links using `storage.from('avasin-library').getPublicUrl(book.file_path)`.
2. `library.html` queries the same published metadata but routes read/download clicks through `createSignedUrl(file_path, 60, options)`. The generated link is valid for 60 seconds.
3. The public pages use the browser Supabase publishable key; no service-role key is embedded in `supabase-config.js`.
4. `admin.html` reads all `library_books` rows, including unpublished entries, and provides metadata editing, publish/unpublish, upload and delete actions.
5. Admin upload accepts PDF or EPUB, applies a browser-side 50 MB size check, creates a UUID-prefixed object path, sets a content type, and uses `upsert:false`. It then inserts the book metadata row with `is_published:true`.
6. Admin edit updates title, author, category and description. Publish/unpublish updates `is_published`.
7. Admin delete removes the Storage object first, then deletes the metadata row. The UI reports an error if object removal fails; if the object is removed but row deletion fails, the row may remain without its file and the UI reports that partial state.
8. User-controlled text in the public library cards and admin library list is escaped before HTML interpolation.

## Findings

### K096-F1 — Storage bucket and table authorization are not defined in checked-in SQL

No `CREATE TABLE` definition or RLS policies for `public.library_books` were found in the checked-in `supabase/schema.sql` or migration set. No bucket creation or `storage.objects` policies for `avasin-library` were found either.

**Impact:** The repository does not establish who can read published metadata, read unpublished records, insert/update/delete rows, upload objects, or remove objects. This is a repository reproducibility gap, not proof that live production lacks policies.

### K096-F2 — Public homepage bypasses the signed-URL path

The homepage uses `getPublicUrl()` for both reading and downloading, whereas `library.html` creates a 60-second signed URL on demand.

**Impact:** If the bucket is public, its objects are publicly retrievable by anyone who obtains the object path, and signed URLs are not the sole access control. If the bucket is private, homepage links generated by `getPublicUrl()` will not provide authenticated access. Confirm the live bucket visibility and decide on one consistent delivery model before relying on private access.

### K096-F3 — Published status is a database-row filter, not a demonstrated Storage authorization boundary

The public page filters metadata by `is_published=true`, but direct object access depends on Storage bucket visibility and `storage.objects` policies. No checked-in policy ties object reads to a published `library_books` row.

**Impact:** Hiding or unpublishing a book row does not, by itself, prove that a previously known object URL stops working. If the bucket is public, a direct object URL may remain accessible independently of the metadata listing.

### K096-F4 — Admin page gate must be backed by table and Storage policies

The admin UI has an authenticated owner gate (reviewed previously), but browser-side page access is not a security boundary for REST/Storage endpoints. No checked-in library-specific policies or RPC authorization definitions were found.

**Impact:** Security depends on server-side RLS and Storage policies that are not represented in the repository. The page gate alone cannot protect table or object operations.

### K096-F5 — File validation is client-side

The admin UI checks filename/type and a 50 MB maximum in JavaScript. No corresponding server-side constraints, MIME verification, file signature checks, malware scanning or upload quota rules were found in checked-in source.

**Impact:** Browser checks can be bypassed by direct API calls. Enforce permitted bucket paths, size/content constraints and upload authorization server-side or through Storage policies and a trusted upload service as appropriate.

### K096-F6 — Delete flow can leave metadata without a file

Deletion removes the object before deleting the database row. If the first operation succeeds and the second fails, the metadata row remains while the file is gone. The UI acknowledges this partial-failure case.

**Impact:** This is recoverable but leaves inconsistent library state requiring a retry or reconciliation process. A server-side transactional/compensating workflow or a retryable deletion state would be more robust.

### K096-F7 — Public card rendering uses escaping

Book title, author, category, description, file path and filename are escaped before insertion into generated card markup. Preserve this pattern; avoid inserting untrusted library metadata into HTML without escaping.

## Recommended next steps (not applied)

1. Obtain explicit authorization for a read-only live Supabase audit. Inspect bucket visibility, `storage.objects` policies, `library_books` table RLS, grants, triggers and any server-side functions.
2. Choose one publication model:
   - **Public library:** explicitly accept that published object files are public and make the homepage and standalone page consistent; document that unpublishing hides listings but cannot revoke copies or previously shared public URLs.
   - **Private library:** remove `getPublicUrl()` from the homepage and require server-authorized short-lived signed URLs; ensure Storage policies prevent direct anonymous object reads.
3. Version-control the authoritative table, bucket, RLS and Storage policies after comparing with live state. Do not blindly create policies without inspecting production.
4. Ensure admin insert/update/delete and Storage upload/remove policies independently enforce site-owner authorization, regardless of client UI.
5. Enforce upload size/type/path rules at the backend; consider file signature validation, scanning and quotas.
6. Add tests for unpublished object access, anonymous direct URL access, non-owner table writes, non-owner Storage writes/removals, signed URL expiry, and delete partial failures.
7. Add a reconciliation/retry mechanism for rows whose object was removed but whose metadata deletion failed.
